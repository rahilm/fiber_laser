# Parity harness: the original binaries under Wine vs the rebuild

Owner: agent J (phase 3). Harness: `/home/dev/scratch/mlaser/parity/` (outside the package).
Tests: `tests/parity/test_parity_*.py`. Latest generated report: `parity/out/report.md`
(machine-readable: `parity/out/results.json`).

The original Mlaser v0.0.1.51_SP1 binaries (32-bit) run under 32-bit Wine 9.0. Two levels:

1. **DLL level** (licence-independent): small i686 mingw programs load an original DLL, call its
   functions with test inputs and print JSON. Python then runs the rebuild's equivalent on the
   same inputs and compares.
2. **App level**: the original `MainApp.exe` under Wine + Xvfb, driven with xdotool. It runs
   inside `unshare -rn`, a user + network namespace whose only interface is loopback. The
   rebuild's card simulator and logging sinks listen on 127.0.0.1 in the same namespace.

Nothing was patched. Licence and dongle checks are untouched; see §4 for where the app stops
and §7 for the machine-level comparison.

## 1. Layout and how to run

```
parity/

  build.sh          builds harness/*.c -> build/*.exe (i686-w64-mingw32-gcc)
  run_parity.sh     build + all DLL-level comparisons + report   (--app: re-run the app scenarios first)
  run_app.sh        app level: `startup` (connect capture), `import` (DXF -> Save As .chf per sample),
                    `lead` (import, select all, 引线 with dialog defaults, Save As),
                    `machine` (machine operations on the card, §7; about 7 min)
  harness/          motion_harness.c, cad_motion_harness.c, circlefit_harness.c, dxf_harness.c, nc_harness.c, nc_job_harness.c, cad_job_harness.c, job_mainapp_harness.c,
                    common.h, *.reg

                    cmp_app_frames.py, cmp_lead.py, cmp_machine.py, app_probe.py, capture_sim.py, make_samples.py,
                    make_machine_samples.py, cmp_job_cad.py, cmp_job_mainapp.py, cmp_job_nc.py, known_diffs.py,
                    run_all.py
  scenarios/        xdotool scenarios (startup_home.json, import_save.json, import_lead_save.json,
                    machine_ops.json generated by machine_ops.py)
  samples/          generated DXF test files (make_samples.py) + the install's dxfTemplate.dxf

  wineprefix/       dedicated 32-bit prefix
  out/              report.md, results.json, app captures (out/app_*/: screenshots, timeline, card_frames.jsonl),
                    out/job/ (cutting-job pipeline dumps, §9.Q3)
```

`./run_parity.sh` takes about 20 s for the DLL level. `./run_parity.sh --app` adds about 15 min
for the app scenarios. `pytest tests/parity` reruns the comparisons. It skips when Wine, the
harness or the orig copy is missing, and `MLASER_PARITY=0` skips it explicitly. It fails only on
errors and on discrepancies **not** listed in `compare/known_diffs.py`.

**Environment (O = observed, needed to make it work):**
- **Wine socket directory.** Ubuntu's wine 9 puts its wineserver socket in `/run/user/<uid>`.
  Without that directory, client and server each pick a different random `/tmp/wine-XXXXXX` and
  every wine command hangs. The app run needs `/run/user/0`, because wine is uid 0 inside the
  namespace. Both directories must be owned by dev. setup.sh creates them.
- **Copy of the install.** `orig/File/ipAdd.ini`: every `*IP=` → `127.0.0.1` (CardIP, ZFIP,
  OnBZFIP, OnBLaserIP, LaserIP, AFIP, AdvAFIP, ECIP, AdvECIP, EC3710IP, MonitorIP),
  `MonitorReconnMaxTime=0`, `Lang=1`. The extracted install is never written. Each app run copies
  `orig/` to `run_orig/` first, because the app rewrites `softPara.ini`, logs and crash-recovery
  state.
- **Wine prefix:**
  - Dead proxy for WinINet/WinHTTP (`127.0.0.1:9`), plus `http(s)_proxy` in the environment.
  - `Direct3D renderer=gdi`: Xvfb's llvmpipe makes wined3d abort.
  - CJK font substitutes (WenQuanYi Micro Hei) and Wine font replacements.
  - `MFC42.DLL`/`MFC42U.DLL` copied from Microsoft's VC6 redistributable. It is downloaded by
    winetricks and checked against winetricks' pinned sha256. MFC42 is a stock Windows component
    that `Dxf2Grp.dll` imports, and without it `CADModule.dll` fails to load.
  - `AppData\Local\NexCut`. MainApp creates `NexCut\Technology` without creating the parent, and
    otherwise stops at "Failed to create Technology folder".
- **Floating point.** The harnesses set the x87 precision to 53 bits (`_controlfp(_PC_53)`), as
  the MSVC runtime of MainApp does. mingw's startup leaves it at 64 bits.

## 4. App level: how far the original gets (O, screenshots in `parity/out/app_*/`)

1. MainApp starts, shows the NexCut splash, and opens the main window (title `v0.0.1.51_SP1`,
   1200×750). The UI stays Chinese despite `Lang=1`. The machine panel (CManuPanel: jog arrows,
   outputs, 开始/暂停/停止, 空走/边框/模拟, 回零位/系统回原/Z回原, mark points) is laid out only
   when the window is enlarged: `app_probe.py` step `winsize` sets 1600×1000.
2. **Connect and download** (§3a of protocol.md, `cmp_app_frames`): RO[0..1] → version 20177,
   `101 := [9999, 5, 0, 0]`, the parameter download, `103 := 1`, read 1032, the 60-word fast-status
   map to 60000, `103 := 1`, servo info 63000×128. Then it polls 1000×36, 50000×26 and 60001×120
   every ~200 ms. All 31 non-poll requests match the rebuild, also with the seeded I/O ports of §7.
3. **Licence gate.** It writes 4 words to 59500 and reads 59500 back (NCModule FUN_10039390 /
   FUN_1003d090) and shows "非授权硬件" (unauthorised hardware) twice. This was not analysed,
   answered, emulated or bypassed. The message does **not** stop the card traffic: the status bar
   reads 控制器<准备就绪> (controller ready) and the poll continues.
4. **Homing.** "硬件连接成功，是否对系统进行回原？" and "系统将进行回原操作，是否继续？", both OK, then
   red light off (when an output is configured), `101 := [2, 3, 0]`, read 1050×3. The log says
   "X、Y轴回原开始" and, once bit 15 of each axis status word is set, "系统回原完成" (mp125,
   MainApp FUN_00598280 over NCModule FUN_10039590). The rebuild's simulator sets that bit (D-20,
   fixed by agent P; before, `capture_sim.py` had to add it or the original waited forever).
5. **Manual machine operations work** despite the warning: jog, step jog, fast jog, mark/return,
   回零位, 系统回原, outputs (红光, 吹气), 激光, 停止, tool and manual coordinate origins, laser
   type. Their card traffic is compared in §7.
6. **Processing is refused.** 开始 (Start), 空走 (Dry Cut), 边框 (Frame), 断点定位 (BreakPt),
   回退/前进 stay disabled, with a drawing loaded, homing complete, no alarm and the card ready.
   The status timer FUN_00598280 enables them only when CManuPanel+0x1e8 == 0, and +0x1e8 is
   the hardware authorisation state that start-up copies from CNCModule +0x2a8 (start-up FUN_00596320 reads it
   after the hardware check; a non-zero value is shown as a message). That is the licence gate; it was
   left alone. Clicking the disabled buttons sends nothing. 模拟 (CAD simulation), 点动切割,
   选中加工 and 循环加工 are enabled but only change UI state (no card traffic).
7. **The CAD part works without the card.** "导入图形" (import) with a DXF followed by "另存为"
   (Save As) writes a `.chf` for all samples (`out/app_files/`).
8. "引线" (lead) after Ctrl+A opens the lead dialog. Its defaults are: lead-in line, 90°, 3 mm,
   r 2; lead-out the same; start mode "自动选择起点位置(长边优先)" (auto, long side first),
   position 0; "只对封闭图形有效" (closed graphs only) checked. OK, then Save As, gives
   `out/app_files_lead/basic_r2000.chf`: leads on the 3 closed contours only, with start_param
   0 (circle), 0.166667 (rectangle: middle of the 100 mm bottom edge) and 0.374474 (closed
   LWPOLYLINE: middle of its longest segment, a 34.8 mm arc).

## 6. What could not be run, and why

- **Frame, Dry Cut, Start (processing), pause/resume/stop during a job, the breakpoint
  registers (RO[23]/RO[24], AutosaveParam) and Backward/Forward.** The original keeps these
  buttons disabled because of the hardware authorisation state (§4.6, licence gate, not
  analysed or bypassed; no other entry point was tried, since that would be a bypass). So no
  FIFO stream (frames, op-3000 steps, process items 103–109, 2001, 9999/3, 9999/18) could be
  captured, and the planned comparison with `compile_job` + `JobStreamer` (step counts, pulse
  deltas, positions, duty/frequency, process items, frame packing) has no original to compare
  with. `cmp_machine` checks that these clicks produce no card traffic and reports them as
  `skip`; if a later original build or setup does stream, it reports an `error` so that the
  FIFO comparison gets written.
- **Follower (跟随, Z回原 with a follower), shutter (光闸), laser emission with a duration.** The
  install has ZF.ZFType 0; 光闸 stayed disabled with LGP.DOLaserGate = 5 seeded; 激光 with 时长 0
  sends only "PWM off". Configuring a follower would change the start-up download and was not
  done.
- **CADModule.dll's motion copy IS driven at DLL level** (agent O, from agent K's debug harness):
  `harness/cad_motion_harness.c` calls the segInterp / segInterp_time copies and the planner
  factory by address (relative to the loaded image base; the planner's vtable is checked). This
  is the main motion reference, since MainApp uses this copy; the MotionCtrl.dll comparisons stay.
- **CADModule.dll's document level** (`newModuleProvider`, 219-slot CCADModule vtable): it needs the
  MFC application state and an OpenGL view, so it was not driven directly. The app level covers
  its DXF import and `.chf` writer instead (§4.7). The sort inside CADModule was not compared.
  Leads, kerf, start, overcut/gap, micro-joints and CInterpMrg's sampler are now compared below the
  document level, on CGlyContour objects built by CADModule's own .chf body loader (§9.Q1).
- **MotionCtrl `newContourSmooth`**: `load` (0x10005f70) takes a vector of 0xd0-byte CAD
  primitives. The line layout and the register-passed `this` were not fully recovered. The shipped
  MotionCtrl.dll is also unused at run time (motion.md §1). Not compared.
- Unknowns: the exact arcInterp mode-1 step rule; the code that cuts some text spline records into Bezier sub-pieces (D-16). The import's graph order is known now (D-12: the mode-5 import sort). The (20, 0)
  placement is CADModule FUN_100ecef0 (20 mm right of the existing drawing), and INSERT pieces are
  joined like any other glyphs: the non-uniform INSERT's arc simply keeps its radius (D-07), so its
  ends miss the lines (agent L, cam.md §1). Machine level: the purpose of read 1050×3 after the
  start-up Go Origin, the slow-jog acceleration (400 = 0.1 × MC.XFastMoveAcc?, I) and the 1000 mm
  continuous-jog distance (I: the soft-limit length, axis word 2), and the frequency 1234 in the
  laser/laser-type PWM-off words (I: PtLaserFreq).

## 8. Verifying against your machine

The Wine harness cannot capture a cutting job (§6: the original refuses Frame/Dry Cut/Start
without its hardware authorisation). On **your own licensed machine** the original runs
normally, so a packet capture of its traffic to the card holds the complete job stream. The
tool `tools/compare_capture.py` (module `mlaser/parity/`, owner agent S) reads that capture,
rebuilds the original's FIFO stream and compares it with the rebuild's `compile_job` for the
same drawing and parameter files. It only reads files and never sends anything to a card.

### 8.1 Safety first (read all of it before you start)

The capture itself is passive, but the original Mlaser will move the machine. Treat every run as
a real machine operation:

1. **Disable the laser physically.** Turn the laser source's key switch off or open its hardware
   interlock (or switch the source off at its own breaker if Mlaser still lets you start; if it
   then raises a laser alarm, use the key/interlock instead). A software setting alone
   (Mlaser's laser button, a dry-run flag) is **not** enough. Close the assist-gas supply.
2. **Dry Cut (空走) first.** It moves along the whole job path with the beam off. Only after a
   Dry Cut compares well, and only if you want the process items checked too (gas, pierce,
   follower, laser PWM items appear only in a real Start), run Start (开始) with the laser
   *still physically disabled* and the gas closed.
3. **A small drawing**, for example a 30 × 20 mm rectangle with a Ø 8 mm hole, placed well inside
   the soft limits and away from clamps. No sheet on the table, or a scrap sheet.
4. **Head height:** raise Z / the follower to a safe height; disable follow during the dry run
   (FC.EnableEmtptMoveFollow off, the default) so the head cannot dive.
5. **E-stop in reach** for the whole run, and nobody inside the machine's working area. Watch the
   first run at reduced speed (lower the layer's cut speed and the rapid speed if you are unsure).
6. Do **not** use the rebuild to drive the machine for this check. The comparison is offline.

### 8.2 Capturing

1. On the Mlaser PC install Wireshark (with Npcap). Find the network interface that faces the
   card: the one IPSet.exe configured with a `10.1.1.x` address (the card is `10.1.1.168`).
2. Start the capture **before** you start Mlaser (so the connect, the parameter download and the
   fast-status map are in the file; the tool also copes with a capture started later). In
   Wireshark use the capture filter `udp port 502` (use `port 502` if `File\ipAdd.ini` has
   `[Soft] AccessType=0`, i.e. TCP). From a command prompt the same is
   `dumpcap -i <interface> -f "udp port 502" -w job.pcapng`.
   Do not use a display filter instead of a capture filter, and do not save "displayed packets
   only" in a way that drops replies: the tool needs both directions.
3. Start Mlaser, connect, home as usual, load the drawing and make the cutting settings you want
   (leads, order, start points). **Save the drawing as `.chf` (File → Save As) right before the
   run**, so the file holds exactly what is cut.
4. Note the head position, the coordinate system (工件坐标系 / 浮动 / 手动) and any edge-seek
   rotation you use.
5. Run the Dry Cut (and later Frame or Start, in separate runs if you like; several jobs in one
   capture are fine). Let the job finish; pausing or stopping is also captured and compared.
6. Stop the capture and save it as `.pcapng`.

### 8.4 Running the comparison

```bash
cd rebuild
.venv/bin/python tools/compare_capture.py job.pcapng part.chf --params NexCut/ \
    --ini ipAdd.ini --jump JumpAddTime.txt --html report.html --json report.json
.venv/bin/python tools/compare_capture.py job.pcapng --list                 # jobs in the capture
.venv/bin/python tools/compare_capture.py job.pcapng --job 1 --dump fifo.txt  # decoded FIFO stream
```

Exit status 0 = IDENTICAL or EQUIVALENT, 1 = DIFFERENT, 2 = error. Options: `--job N` (default:
the job with the most steps), `--kind frame` to compare a Frame (边框) run, `--dry-run yes|no`
(default: detected from the stream), `--start X,Y` (default: the card's last position read
before the first frame), `--offset DX,DY` (default: estimated, `0,0` disables), `--scaling
card|xml` (default: adopt the card's step scale and period like the rebuild UI), `--cam
sort_mode=5` (any `CamParams` field, if the original's order settings differ from the rebuild's
defaults), `--tol` / `--path-tol` (pulses), `--card HOST[:PORT]`.

What it does (`mlaser/parity/capture.py`, `pcap.py`, `report.py`):

* **Reading:** pcap and pcapng in pure Python (Ethernet with VLAN tags, Linux SLL/SLL2, Npcap
  loopback, raw IP; IPv4 fragments; UDP; TCP with stream reassembly for AccessType=0, including
  out-of-order, retransmitted and overlapping segments). Checksums are not checked (offload).
* **Card traffic:** every request and reply is decoded with `mlaser.protocol.frames` and paired
  by transaction id. An identical re-send with the same id is a retransmission of the original's
  retry loop (FUN_1001d6d0); a frame re-sent with a new id but the same sequence number (the
  "second fillFifo" retry, FUN_10052e90) counts once. Status reads give RO[15]/RO[16]/RO[19]
  and the axis positions (plain `2000×50` or fast `60001×120` reads through the 60000 map), and the
  parameter-block reads give the card's scaling (FUN_10039f20).
* **Jobs:** a job starts at a FIFO clear (103 := 1) followed by `write(102, [seq, items…])`
  frames; the items in sequence order are the original's wire, comparable item for item with
  `Job.wire`. Sequence gaps, conflicting re-sends, frames without an OK reply and the flow
  control (RO[16] ≥ frame + 2000 before each frame, frames per fill) are reported.
* **Rebuild side:** `Machine.from_dat_dir(--params, --ini, --jump)`, the card's step scale and
  period when the capture has them, the layers from LayerPara.xml, `compile_job(drawing,
  start = the captured start position, dry_run)`. When the original placed the drawing through a
  coordinate system, the placement offset is estimated from the captured path (bounding box and
  first cut point of the path after the first rapid; the candidate that puts the most of the path
  within `--path-tol` wins) and applied as `doc.extra["job_offset"]`.
* **Checks** (`*` = core, decides the verdict): step count\*, per-step deltas, cumulative position
  time-aligned\* (max deviation in pulses), path deviation spatial\* (Hausdorff, order
  independent), end position\*, duty\* / frequency (laser-on steps)\* / power\* per step, process
  items in order with values\*, their step positions, frame packing (and whether the original's
  frames follow the 1200-byte rule of `frames.build_fifo_frames`), frame sequence numbers, flow
  control, job time (step replay, timed waits, wall clock 103 := 2 → RO[19] = 0), the
  pause/stop sequence against the rebuild's `UiController.stop` writes, and the end position the
  card reported against start + Σ steps.
* **Verdict:** IDENTICAL (the item streams are equal), EQUIVALENT (all core checks pass, some
  secondary ones differ) or DIFFERENT. The report gives the first divergence at item level and at
  step level with ± `--context` items/steps, the cumulative positions there and the nearest
  process item, the first duty/frequency/power difference, the process-item diff, and
  statistics. When the divergence lies inside a run of identical items (a dropped or extra step
  in a straight run), the report gives the run's first index too: the difference is somewhere in
  that run. The HTML report adds plots (matplotlib, optional): path overlay with laser-on runs,
  deviation along the path, duty and frequency per step, and a zoom on the first divergence.

### 8.5 Reading a DIFFERENT verdict

* Paths that agree spatially (Hausdorff small) but not time-aligned: same geometry, different
  speed profile or order. Check `--cam sort_mode`, the layer speeds in LayerPara.xml and the
  planner parameters; the first step divergence shows where the timing starts to differ.
* A constant offset of the whole path: the placement (coordinate system, edge-seek rotation; the
  rotation is not estimated) or the start position. Try `--offset` / `--start`.
* Laser fields only: the speed curves (power/frequency vs speed), slow start/end blocks or
  micro-joint settings (protocol.md §10.4).
* Process items only: protocol.md §10 (sequences per ManuItem class). Dry runs have few or no
  process items; use a real Start with the laser physically disabled to check them.
* The card-reported end position differs from start + Σ steps: the job was interrupted, or the
  card's position counts per mm (`--position-ppm`) differ from what the tool assumed.

### 8.6 Tests and limits

`tests/test_parity_capture.py` (22 tests) builds synthetic captures from the rebuild's own
simulator traffic (`mlaser.parity.synth.record_job`, written with the pure-Python pcap/pcapng
writer in UDP and TCP form, several link types), checks that the tool reports IDENTICAL for the
rebuild's own job (also with retransmissions, a re-sent frame, a dry run with an estimated
placement offset, a Frame run, TCP + pcapng + .chf), and that a dropped step, a changed duty and
two swapped process items are each detected and located (step / item index); a stopped job's stop
sequence matches the rebuild's.

Limits: the synthetic tests prove the tool, not the rebuild: the first real capture is the first
real comparison. Not handled: edge-seek rotation estimation (pass the rotated drawing), resumed
jobs after a breakpoint (each resume is a separate job in the capture, compared as a whole job),
bus-card step items (14-bit speed variant, protocol.md §5), IPv6, and captures that lost packets
(missing frames show up as sequence gaps). The position counts per mm come from the card's
system block in the capture; without it the rebuild's default (1000, INFERRED) is used.
